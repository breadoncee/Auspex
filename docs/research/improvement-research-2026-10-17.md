# Auspex improvement research

Research date: 17 October 2026 (Asia/Manila). Code inspected: `ebf61d48af315cea261b512c2f3737651692befc`, version 1.2.0. Scope: next improvements to the existing macOS menu bar monitor; research and recommendations only. No application changes, benchmarks, or interactive accessibility audit were performed for this note.

## Recommendation

Improve trust in the existing readings before expanding the number of readings. The strongest next release would make missing data honest, explain memory and swap clearly, stop treating every mounted volume as a full physical drive, and make the compact panel more personal. Follow with useful short history and easier signed updates.

The app already has valuable foundations: light/dark/system appearances, semantic colors, increased-contrast borders, Reduce Motion/Transparency handling, optional swap availability, runtime temperature-symbol checks, bounded collection work, and reduced polling while closed or asleep. Preserve these while improving the gaps below. These are code observations, not claims of full platform certification.

## Ranked roadmap

Effort estimates are engineering judgments for this small codebase: S = a few focused days; M = several days to roughly two weeks including validation; L = a larger separate feature. They exclude acquiring signing credentials and waiting for additional hardware.

| Priority | Improvement | User value | Effort | Concrete completion check |
|---|---|---|---|---|
| 1 | Trustworthy readings and storage classification | Stops unavailable values looking healthy or full; directly addresses confusing friend screenshots | High; S–M | Inject collector errors: show unavailable/stale, retain a dated last-good value; read-only installer images do not produce writable-drive warnings, while a genuinely full writable disk still does |
| 2 | Memory pressure and swap interpretation | Answers whether a high number needs attention, beyond displaying RAM percentage | High; S–M | High RAM with normal pressure is not presented as a fault; zero swap, unknown swap, warning pressure and active swap I/O are distinguishable; swap is never added to resident RAM |
| 3 | Personal, readable compact UI | Keeps the user's temperature and memory priorities visible; reduces scrolling | High; S–M | Temperature menu bar option, persistent card ordering/visibility and restored defaults; logo remains visible; keyboard/VoiceOver and both appearances pass a defined fixture matrix |
| 4 | Timestamped short history and optional sustained alerts | Shows what changed when the Mac became slow, without a large dashboard | Medium–high; M | A chosen 60-second or five-minute window is truthful at every refresh setting; pauses are gaps; accessible summaries exist; alerts require opt-in, duration and cooldown |
| 5 | Easier, trustworthy distribution and measured efficiency | Friends can install and update reliably; the monitor stays inexpensive to run | High for distribution; M | A freshly downloaded Developer ID-signed, notarized, stapled build opens on a second Mac; an update from an old build succeeds; idle/open-panel energy measurements are recorded |

These priorities group related work rather than imply that signing or energy work must wait for every UI feature. Start signing preparation and baseline performance measurement alongside priorities 1–2.

## 1. Make availability, freshness and disk type explicit

**Code observations.** [`MemoryCollector`](../../Sources/Collectors/MemoryCollector.swift) returns normal pressure when the pressure query fails. [`SystemMonitor`](../../Sources/Model/SystemMonitor.swift) can subsequently replace a pressure event with that sampled value. [`PanelView`](../../Sources/Views/PanelView.swift) declares the panel Live whenever one global `lastUpdated` exists, even though disk readings are normally ten seconds apart and thermal readings three seconds apart. A collector failure does not have a distinct freshness state. [`DiskCollector`](../../Sources/Collectors/DiskCollector.swift) converts absent available capacity to zero and does not request read-only status. Consequently, a mounted read-only installer image or an unavailable capacity result can resemble a full drive. The friend's OrbStack screenshot alone does not prove which case occurred.

**Sourced facts.** Apple's capacity example explicitly handles an unavailable result, and its important/opportunistic APIs answer different storage-allocation questions. Important-usage capacity is an estimate for storing important resources; it should not be promised as an exact universal Finder match. Foundation exposes read-only and local-volume properties. APFS volumes in the same container share free space, so their capacities must not be summed as independent physical disks. [Capacity queries](https://developer.apple.com/documentation/foundation/checking-volume-storage-capacity), [volume status keys](https://developer.apple.com/documentation/foundation/urlresourcekey/volumeislocalkey), [APFS space sharing](https://support.apple.com/guide/disk-utility/add-delete-or-erase-apfs-volumes-dskua9e6a110/mac).

**Recommendation.** Represent each reading as a value plus collection time and status: reading, current, stale or unavailable. Keep last-good values visibly dated after transient failures. Preserve a valid pressure event instead of replacing it with a fabricated normal result. For storage, distinguish writable local/external volumes, read-only volumes, and other mounts; offer hide/show preferences. Label capacity as Available with a brief explanation of reclaimable space where relevant. An actual zero on a writable volume must remain zero. Do not hide a volume merely because its name resembles a development tool, or assume all virtual-volume zeros are errors.

**Acceptance checks.** Fixtures for missing keys, errors, valid zero, read-only disk image, external writable disk, network mount, duplicate names and APFS siblings; verify no invented physical-disk total. Freshness survives sleep/wake and partial collector failures. A global successful CPU sample cannot make failed storage look newly current.

## 2. Explain memory and swap; measure activity separately

**Code observations.** Resident RAM is currently an estimate of anonymous non-purgeable pages plus wired and compressed storage. Swap usage is correctly optional and separate. Memory pressure already exists, but the overview's biggest number remains RAM percentage. Current pressure mapping uses dispatch-style values 1/2/4.

**Sourced facts.** Apple defines pressure using several inputs, including swap rate, free memory, wired memory and cached files. Swap Used describes startup-disk space used for moving unused data between disk and RAM. RAM occupancy alone therefore cannot reproduce Apple's pressure measure. [Activity Monitor memory definitions](https://support.apple.com/guide/activity-monitor/actmntr1004/mac).

XNU exposes lifetime `swapins` and `swapouts` page counters separately from resident counts. Its pressure sysctl converts internal states to dispatch flags before exporting them; the internal kernel enum values are not the same thing as this sysctl's result. The existing 1/2/4 mapping should not be replaced with internal 0/1/2/3 values. Apple documents `DispatchSourceMemoryPressure` as monitoring system pressure changes. [VM counters](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/mach/vm_statistics.h), [pressure conversion and sysctl implementation](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/kern/kern_memorystatus_notify.c), [public pressure source](https://developer.apple.com/documentation/dispatch/dispatchsourcememorypressure).

**Recommendation.** Keep RAM used and Swap used, promote the pressure label beside them, and add plain help such as “Swap is disk space used by virtual memory; pressure shows how efficiently memory is meeting current needs.” Add a small swap trend first. If users need to distinguish occupied swap from current swapping, derive swap-in/out activity from counter deltas, real elapsed time and the actual host page size. Reset baselines after pauses/counter resets. Label this as VM swap activity, not physical SSD writes. Swap growth, current swap occupancy, storage throughput and SSD wear are different measurements; no SSD-life estimate follows from the current field.

The sysctl is visible in Apple's source but is not equivalent to a stable, documented Foundation contract. Retain best-effort handling and the public event source; show unknown until a trustworthy initial state exists. Keep “resident estimate” wording rather than promise byte-for-byte Activity Monitor parity.

**Acceptance checks.** Simulated 90% RAM with normal pressure; warning/critical events followed by failed polling; zero/nil swap; increasing/decreasing counters; nonpositive intervals and wake resets; page-size conversion. Compare a short captured sequence with Activity Monitor and `vm_stat` without intentionally exhausting the user's memory. Do not diagnose SSD damage from large occupied swap.

## 3. Make the panel fit the person and preserve temperature

**Code observations.** The panel has a fixed 400-point width and maximum 740-point height, and repeats CPU/memory overview and detail. Menu choices are icon only, CPU and memory. There is no temperature menu choice or card-order preference. Charts and captions contain small secondary text and some single-line labels. Existing accessibility modifiers are a useful start, not evidence of a completed audit.

**Recommendation.** Offer a compact overview plus expandable detail, with Temperature and Memory kept prominent by default for this user. Allow card hiding/reordering with a reset option. Add one selectable temperature value to the menu bar while keeping the pulse icon and a strict width budget; avoid several competing inline metrics. If no numeric sensor works, show an unavailable temperature or labeled thermal state rather than a fake temperature. Provide an Open Activity Monitor action from CPU/Memory details before implementing expensive continuous process enumeration.

Distinguish a missing glyph from an entire menu item hidden by macOS. Apple says an inserted menu extra is not guaranteed visible when space is constrained, and documents a per-app Allow in the Menu Bar setting. Add a short recovery guide and a reopen path; keep the selected inline metric narrow. [MenuBarExtra visibility](https://developer.apple.com/documentation/swiftui/menubarextra/init(isinserted:content:label:)), [menu bar settings](https://support.apple.com/en-ie/guide/mac-help/mchlad96d366/27/mac/27).

Apple recommends semantic colors and accessible interfaces with non-color status cues and readable text. Use those principles to validate the existing design rather than restyle it indiscriminately. [Color](https://developer.apple.com/design/human-interface-guidelines/color), [accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility), [menu bar](https://developer.apple.com/design/human-interface-guidelines/the-menu-bar).

**Temperature reliability.** The code dynamically loads private IOHID functions and infers the CPU/SoC sensor group from names including CPU, die, PMGR and ACC. Treat the average as an inferred sensor-group reading, not an Apple-defined package temperature. Keep the public `ProcessInfo.thermalState` alongside it and consider a selected sensor option after hardware validation. Use system thermal state for system-level severity; the generic 65°C/85°C color bands in `Thresholds` are application choices, not researched safety limits for every Mac. Apple's public thermal APIs provide coarse system state and notifications; App Store rules require public APIs, so a future store build would need a separate capability decision. [ProcessInfo](https://developer.apple.com/documentation/foundation/processinfo), [thermal guidance](https://developer.apple.com/library/archive/documentation/Performance/Conceptual/power_efficiency_guidelines_osx/RespondToThermalStateChanges.html), [App Review 2.5.1](https://developer.apple.com/app-store/review/guidelines/).

**Acceptance checks.** Retain functioning temperature display and test absent symbols, no sensors, duplicate names, failed client creation and sleep/wake recovery. Add bounded retries after transient initialization failures, with no busy loop. Test light/dark/system overrides, Increase Contrast, Reduce Transparency/Motion, keyboard access, VoiceOver, smaller screens/external displays, long names and larger text. Use deterministic previews for zero/nil swap, warning pressure, no battery and full/read-only disks. A screenshot render is not an interactive accessibility audit.

## 4. Add history that tells the truth

**Code observations.** Current histories are 40 scalar samples, cleared when opening or waking. With a 0.5–5 second interval, the nominal visible range is roughly 20–200 seconds; charts have no timestamps. Network upload and download autoscale independently. CPU accessibility states current usage, while network sparklines are hidden from accessibility.

**Recommendation.** Store timestamped points in a bounded in-memory buffer and offer a clear 60-second or five-minute range. Add pressure, swap and temperature history to existing CPU/network trends. Show elapsed range and a scale; use a shared upload/download scale when comparing them. Draw gaps after collection pauses rather than implying continuous measurements. Keep background recording off by default or make its energy tradeoff explicit. Short history retained while open should not silently become all-day polling.

Apple's chart guidance supports clear scales and useful context. Existing custom charts can use an accessibility chart descriptor; a wholesale Swift Charts migration is unnecessary just to expose a history summary. Provide current/min/max and trend text, not a screen-reader announcement every refresh. [Charts HIG](https://developer.apple.com/design/human-interface-guidelines/charts), [custom-chart accessibility](https://developer.apple.com/documentation/swiftui/view/accessibilitychartdescriptor(_:)).

**Acceptance checks.** Change refresh interval mid-window; reopen after a minute; sleep and wake; fill the buffer beyond capacity; compare unequal upload/download traffic. The labeled time span remains correct and VoiceOver can obtain meaningful history. If alerts are later added, require opt-in, a sustained condition, cooldown and a recovery state; a brief CPU spike or large stable swap occupancy should not trigger a generic danger alert.

## 5. Distribution and energy: reduce friction without adding heavy machinery

**Code observations.** `Makefile` signs completed bundles ad hoc; `project.yml` disables hardened runtime. README installation currently asks users to remove quarantine. There is no updater in Settings. README's claimed SDK validation is stale relative to the recent Xcode 27 release work; correct build provenance when the next release is actually tested.

**Sourced facts.** Apple's modern notarization flow requires an appropriate Developer ID signature, hardened runtime and a secure timestamp. `notarytool` submits software; stapling attaches the ticket and improves offline installation behavior. Apple recommends testing the actual distributed package, preferably on another Mac. [Notarization requirements](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution), [distribution packaging and testing](https://developer.apple.com/documentation/xcode/packaging-mac-software-for-distribution).

**Recommendation.** Add a reproducible Developer ID/notarization pipeline when credentials are available. Validate signature, notarization ticket, launch, temperature capability, menu logo and settings migration on the downloaded archive. Keep release metadata and version/build numbers consistent. For the smallest immediate improvement, add a version-aware Check for Updates action that opens the release page. For in-app installation, evaluate maintained Sparkle 2 as an explicit new dependency rather than build a custom installer. Sparkle's own documentation recommends HTTPS, Developer ID/notarization where possible, EdDSA-signed archives and protected signing keys; its appcast uses increasing bundle build versions. [Sparkle official integration/security documentation](https://sparkle-project.org/documentation/). This is first-party documentation from the project, not an Apple framework. Its dependency and release maintenance would change Auspex's current zero-third-party-dependencies promise.

**Energy recommendation.** Keep the existing single timer, tolerance, bounded queue and sleep/closed-panel behavior. Measure before optimizing. Add Low Power Mode and thermal notifications to reduce optional updates instead of increasing background polling for new features. Apple's current power guidance recommends reducing optional work in Low Power Mode or elevated thermals; timer tolerance gives the system scheduling flexibility. [Power notifications](https://developer.apple.com/documentation/xcode/responding-to-power-notifications), [timer tolerance](https://developer.apple.com/documentation/foundation/timer/tolerance), [performance measurement](https://developer.apple.com/documentation/Xcode/improving-your-app-s-performance).

**Acceptance checks.** Record ten-minute idle icon-only, idle CPU/memory, and open-panel runs on the same Mac under controlled conditions: Auspex CPU time, wakeups, memory footprint, collector latency and Energy Impact. Repeat with Low Power Mode and after sleep/wake. Treat targets as measured project budgets, not universal CPU-percent guarantees. Verify no polling timer in icon-only idle and no unbounded work queue during repeated Refresh. Test a signed old-to-new update and a fresh offline launch on another Mac, plus the exact shipped zip signature and version.

## Small product comparison

First-party product material shows that these are established utility needs: Stats lists configurable menu modules and sensors, while iStat Menus presents pressure/swap history, top apps and menu ordering/visibility. The useful lesson for Auspex is focused customization and context, rather than copying every metric. This comparison does not establish either product's accuracy or Auspex's energy cost. [Stats project](https://github.com/exelban/stats), [iStat Menus](https://bjango.com/mac/istatmenus/).

## Limits and next implementation slice

The source research establishes API semantics and platform guidance; it does not validate every sensor on every Apple Silicon generation, prove physical SSD wear, or certify an energy improvement. Apple open-source `main` explains current source behavior but is not a guarantee that every shipped macOS build is identical. A small supported-macOS/hardware test matrix remains necessary.

Recommended next slice: availability/freshness states, storage type/capacity correctness, pressure-focused Memory wording and deterministic UI fixtures. Then add temperature menu selection and timestamped short history. Defer GPU/fan control, disk cleanup, full process monitoring and SSD-life predictions until user demand and reliable APIs justify their complexity.
